# Widget API Naming and Configuration Validation Boundaries

**Status:** Proposed
**Date:** 2026-10-25
**Sources:** historical UI/API review, U4/F6–F8; the adopted mapping is retained in [spec 0041](../spec/0041-widget-api-naming-and-configuration-validation.md) R1–R3/R7; refinement conversation approving the complete naming mapping, repository-wide caller migration without old aliases, explicit invalid-configuration rejection with derived overflow left to layout, and a spec → tickets endpoint.
**Related:** [ADR 0079](./0079-defer-root-construction-and-unify-content-slot-boundaries.md), [ADR 0080](./0080-unify-child-cardinality-and-replacement-semantics.md), [ADR 0081](./0081-preserve-click-naming-and-standardize-disabled-builders.md), [ADR 0082](./0082-ui-thread-local-widget-callbacks.md), [ADR 0083](./0083-composable-buttons-and-shared-control-surfaces.md), [ADR 0084](./0084-explicit-layout-trees-and-local-configuration.md), [ADR 0086](./0086-normalized-key-chords-and-private-runtime-control.md).

## Context

U1–U3 have landed code, while U4 groups the remaining wrapper/naming, appearance-validation and non-layout named-configuration work. The original naming checklist was a recommendation, not an implemented API. The user approved adopting its complete mapping and direct caller migration rather than retaining duplicate synonymous APIs.

Current appearance inputs differ in their failure behavior: icon sizes can be silently ignored, field padding can become zero, separator thickness can fail only at layout, and public style/theme input fields can bypass any explicit validation. Consuming a raw configuration does not itself establish validity. The earlier layout-specific decision in ADR 0084 already distinguishes invalid scalar inputs from geometry that cannot be computed under parent constraints.

## Decision

1. **Adopt the full U4 mapping in spec 0041 R1–R3/R7, without a compatibility naming layer.** The selected names include `ExternalSurface` (formerly `CustomPaint`), `NotificationCard` and its style/placement types, `ActionHandler<A>` (formerly `Actions<A>`), `ShortcutMap<A>` (formerly `Shortcuts<A>`), and `CrossAxisAlignment` (formerly `Alignment`). Migrate affected module names, exports, repository callers, fixtures and documentation together. These are selected names, not claims that the current code already exposes them.
2. **Separate positioning from cross-axis stretch.** Notification placement and close positioning use the established `PositionAlignment`/`Alignment2D` concepts, not the Stretch-capable cross-axis type. Flex keeps its real Stretch behavior. This extends, rather than replaces, ADR 0084's layout/position distinction.
3. **Make method vocabulary describe ownership and operation.** Adopt spec 0041 R2–R3's constructor, property, callback and query mappings. Constructors take necessary configuration rather than children; single-slot `.child` and `.child_with` replace the same slot, with independent content-Fiber lifetime preserved. Widget configuration queries use `get_property`; controllers and immutable values do not acquire that prefix mechanically. `requested_offset` must remain distinct from committed `ScrollMetrics::offset`. Keep `on_click` versus `on_activate`, focus eligibility versus disabled, ordinary UI-local callbacks and existing external-provider ownership/timing unchanged.
4. **Reject illegal appearance configuration explicitly; do not hide it through no-op or zero substitution.** Equivalent entry points share validation semantics. Dimensions, padding, spacing, stroke widths, radii and placement inset must be finite and nonnegative; notification maximum width must additionally be positive. Ordinary solid-color components must be finite, without a newly imposed [0,1] restriction. Failures dependent on authoritative parent constraints or overflow from individually valid values remain layout errors under the existing atomic-layout contract. The user confirmed these domains during the 2026-10-25 refinement; existing material caps remain distinct from invalid input.
5. **Keep the scope bounded.** This is U4/F6–F8, not a repetition of U1–U3, a new UI runtime, a generic Props/style/Container system, a host/GPU result redesign (U5), or a renderer-order redesign (U6). Preserve the prior layout, slot, runtime and application ownership contracts.
6. **Keep plain input configurations and validate at every consuming seam.** Direct configuration entry points accepting raw invalidatable input return Result, including static theme/style consumption. Public input fields are not proof of validation. Signal-driven themes and dynamic foreground callbacks validate each consumed value and panic explicitly with the invalid field when it is illegal; do not silently retain the old theme, replace the value, or add Result propagation to Component::build/Runtime. Ordinary view! keeps its established final-node Result handling; no intermediate-chain rewriting is selected. This preserves recoverable direct construction without redesigning the runtime error contract.
7. **Use named material input while retaining current bounds and product ownership.** Replace public tone/rim array input with local named configuration. Preserve finite-input checks, existing negative-value rejections, and existing caps/clamps for otherwise valid inputs, including the blur/refraction sampling limits. Compact GPU upload arrays may remain internal; application-owned glass recipes and their visual/interaction behavior do not move into the widget crate.
8. **Recommend root imports without introducing a prelude.** Complete the root exports of common widgets, including Stack/TextLabel, and Component/BuildCx/View, alongside the existing construction/extension traits. Detailed configurations remain available in their owning modules; do not export every internal type merely to shorten imports.

## Consequences

- This is an intentional public API break; old names are not kept as aliases. Repository integration must include tests, macro compile fixtures, examples and docs, not only production call sites.
- Explicit rejection makes erroneous configuration visible, while valid business defaults, interaction semantics, layout constraints and appearance roles must remain intact.
- A selected name does not promise runtime identity preservation across a changed type/tree or remove the existing native focus, IME and real HMR acceptance obligations.
- **Refinement completion (2026-10-25):** The user also confirmed the explicit domains, direct Result versus dynamic-consumption panic boundary, retained material caps and root-import policy. The selected requirements remain in [spec 0041](../spec/0041-widget-api-naming-and-configuration-validation.md); former ticket set 0019's [evidence and remaining acceptance](../spec/0041-widget-api-naming-and-configuration-validation.md#delivery-evidence-and-remaining-acceptance) now live there. This record establishes neither implementation progress nor test acceptance; error-type/helper spellings remain implementation choices within the settled behavior.
