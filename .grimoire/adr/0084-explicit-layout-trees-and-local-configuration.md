# Explicit Layout Trees and Local Configuration

**Status:** Proposed
**Date:** 2026-10-24
**Sources:** [UI_API_REVIEW.md](../../UI_API_REVIEW.md) F5; refinement conversation accepting breaking repository-wide migration, inclusion of the F8 layout types and related F7 validation contract, and a spec-only endpoint.
**Related:** [ADR 0032](./0032-view-macro-rust-expression-grammar.md), [ADR 0079](./0079-defer-root-construction-and-unify-content-slot-boundaries.md), [ADR 0080](./0080-unify-child-cardinality-and-replacement-semantics.md), [ADR 0083](./0083-composable-buttons-and-shared-control-surfaces.md).

## Context

The revised F5 proposal favors Flutter-style explicit component composition rather than generic layout-wrapping methods. Current Harbor already has a Rust-expression view macro, deferred component construction, shared child capabilities, parent-authoritative constraints and one shared Flex engine. Its remaining API gaps include a leaf-only SizedBox, positional inset parameters, separate horizontal/vertical Align settings and long local Flex configuration chains.

The user accepted the recommended scope and selected one requirements spec without ticket slicing or implementation. This record captures the settled architectural boundaries, not implemented behavior. Clarifications (2026-10-24): the user selected ordinary named input configurations with component-boundary validation returning Result (option A), requested automatic handling in view! without repeated question-mark operators, and accepted construction-site panic on Err, macro-external recovery and a final-node-expression-only handling boundary. The user also accepted finite, nonnegative requested dimensions, gaps and individual inset sides, with overflow from combining valid inputs remaining a layout error.

## Decision

1. **Use explicit layout components, not a universal layout extension API.** Layout, decoration and flex wrappers remain visible in the declared tree. Do not add generic padding, size, alignment, decoration or expanded wrapping methods to ComponentExt. Retain the existing keyed identity entry point and useful component-local configuration methods. A universal Style or Container is not part of this change.
2. **Extend SizedBox itself to an optional single-child size component.** Preserve its child-free placeholder purpose and background-color capability. Support two specified dimensions and single-axis requests; an unspecified dimension is distinct from zero or infinity. Requested dimensions remain subordinate to parent constraints. Specified axes become tight child constraints after parent enforcement; unspecified axes inherit parent constraints and use child measurements, or zero natural size without a child. The child is placed at the local origin without adding clipping, focus stops or input handling. Replace the public Size-only configuration with private optional-axis configuration and read-only access; do not preserve a misleading public size field.
3. **Share named inset and two-dimensional positioning configuration.** Padding and Align use one Insets concept. Align uses an Alignment2D positioning value without Stretch; Row/Column retain real cross-axis Stretch. Preserve Align's existing constraint and inset semantics rather than mechanically replacing it with a different wrapper order or adopting Flutter's full measurement behavior.
4. **Keep Flex configuration local and shared.** Row, Column and Flex share a local FlexOptions configuration entry point and the existing Flex engine. Configuration and supported short builders use the same underlying settings and validation path. Axis remains a constructor concern and children remain governed by the shared slot protocol. Do not introduce a new macro property language or generic style object.
5. **Accept targeted breaking migration and coordinate validation.** Migrate affected repository consumers rather than maintain indefinite duplicate layout APIs. Include F8's layout-related types and the F7 validation contract needed by these components, not a repository-wide F6–F8 rewrite. Insets and FlexOptions remain ordinary named input configurations. Relevant component constructors and numeric setters validate raw input at the boundary and return Result; handwritten callers can recover from invalid configuration. Do not silently ignore invalid values, normalize them to zero or make all APIs panic. Errors requiring parent constraints or computed geometry remain layout diagnostics/errors.
6. **Preserve established runtime and application boundaries.** ADRs 0032, 0079 and 0080 continue to govern expression evaluation, deferred construction, slots and identity. Flexible metadata still belongs to the immediate layout parent. Keep application command sources, controllers, focus handles and popup generation validation unchanged. Keep GlassAppearance's filtering/decoration/clipping preset and construction timing. A fixed width plus height cap is not a fixed two-dimensional size.
7. **Automatically resolve fallible node results in ordinary view!.** At both root and child positions, accept an ordinary node value or a final Result containing that node. Ok continues through the same deferred construction and child-capability protocols. Err produces a clear construction-site panic containing the configuration error and source location; do not silently skip the node or substitute defaults. Ordinary view! still returns View. Recoverable construction remains available by handling Result outside the macro and supplying a valid node. Automatic handling applies to the final node-expression result, not arbitrary nested Rust expressions or intermediate method-chain calls. Prefer local Options values for multi-property declarations; this is not authority to insert hidden unwraps throughout Rust syntax. Preserve single evaluation, sibling order, children-before-parent expression evaluation and branch laziness.
8. **Use finite, nonnegative scalar layout inputs and keep combination overflow in layout.** Requested fixed dimensions, gaps and each individual Insets side must be finite and nonnegative; zero is valid. NaN, either infinity and negative values are rejected through the component-boundary Result contract. An omitted axis remains absence and a parent maximum may remain positive infinity under the existing constraints contract. Individually valid values are not rejected merely because their later combination overflows: opposing inset sums, child-count-dependent gap totals and other geometry combinations report layout errors through the existing atomic layout path. This fixes the previously open F7 numeric domains without adding a construction-time aggregate-size restriction.

## Consequences

- UI declarations expose component nesting and concentrate a node's local layout settings without replacing the runtime or layout engine.
- SizedBox's capability and configuration changes require consumer and leaf-fixture migration; the general prohibition on attaching children to leaves remains intact.
- Equivalence must cover constraints, wrapper order, paint/clip/hit-test behavior and state/focus lifecycle, not just outer dimensions or fewer lines of code. Structural rewrites do not acquire cross-parent state preservation through keys.
- Ordinary Rust expressions and child capabilities remain the construction surface. Automatic fallible-node handling now requires construction-support work; it does not itself authorize a new attribute DSL or a runtime redesign.
- The selected requirements contract is [spec 0038](../spec/0038-explicit-layout-components-and-fallible-view-nodes.md). No implementation, acceptance results, ticket set or execution plan is established by this record.
