Handling the confirmed result here is a natural extension of its coordination role — it is the only module that has access to all three.

New Types

None. The existing Button widget, ConfirmationResult::Confirmed variant, and Arc<AtomicBool> signaling pattern from T0003 already provide the abstractions needed. The Paste button is a second Button with a different label and callback target. No new widget, intent type, or mode-reading abstraction is required.

Design Decisions

  • Use Arc<AtomicBool> for confirmed signal — identical pattern to T0003's cancelled flag. The Button's on_click stores the atomic; the App reads it after widget dispatch. No new intent system required.
  • Handle y at window-level, before widget dispatch — consistent with T0003's Escape and n cancellation shortcuts. Window-level shortcuts bypass the widget tree, preventing accidental double-processing.
  • Defer PTY write to the App, not the Widget Runtime — ADR 0008 and ADR 0009 require that the confirmation Runtime has no knowledge of terminal types. The Widget emits a flag; the App translates it to a terminal command.
  • Reuse existing PasteText terminal command path — terminal_worker's PasteText handler calls terminal.screen().input_modes() at send time, automatically satisfying the requirement that InputModes are read when confirmation occurs, not when the dialog opened.
  • Place Paste before Cancel in the Row — Runtime::focus_first_focusable() finds the first focusable widget in tree order. Paste-first means the confirmation action is the default, requiring an explicit Tab or click to cancel.
  • Keep raw_text unchanged throughout the confirmation lifecycle — the Widget Runtime never sees or modifies the paste content. It is stored on ConfirmationWindow and forwarded verbatim on confirm.

Step 3: Modify build_confirmation_root to add Paste button in a Row layout

Files: src/app/confirmation.rs

Action: Change the function signature to accept both cancelled and confirmed Arc<AtomicBool>. Replace the single Cancel button with a Row containing Paste and Cancel buttons. Place Paste first for default focus priority. Add a SizedBox spacer between the header and the button row. Import Row from harbor_widget. 

use harbor_widget::widgets::row::Row;

fn build_confirmation_root(
    line_count: usize,
    cancelled: Arc<AtomicBool>,
    confirmed: Arc<AtomicBool>,
) -> impl harbor_widget::view::Component {
    let header_text = format!("Paste {} lines?", line_count);

    Padding::new(24.0, 16.0, 24.0, 16.0).child(
        Column::new()
            .child(TextLabel::new(header_text))
            .child(SizedBox::new(harbor_widget::layout::Size::new(0.0, 24.0)))
            .child(
                Row::new()
                    .child(Button::new("Paste").on_click(move |_ctx| {
                        confirmed.store(true, Ordering::SeqCst);
                    }))
                    .child(SizedBox::new(harbor_widget::layout::Size::new(12.0, 0.0)))
                    .child(Button::new("Cancel").on_click(move |_ctx| {
                        cancelled.store(true, Ordering::SeqCst);
                    })),
            ),
    )
}
Outcome: The confirmation dialog renders a Paste button (default-focused) and Cancel button in a horizontal row. Click or Enter on Paste sets the confirmed flag.

Step 4: Modify ConfirmationWindow::handle_event to check y key and confirmed flag

Files: src/app/confirmation.rs

Action: Add y / Y character key match to the window-level keyboard shortcuts, returning ConfirmationResult::Confirmed. After widget dispatch, check self.confirmed.load(Ordering::SeqCst) and return Confirmed if true. The check order is: CloseRequested → keyboard shortcuts (Escape/n/Y → Cancel, y → Confirm) → widget dispatch → confirmed flag check. 

// Window-level shortcuts — before widget dispatch
WindowEvent::KeyboardInput {
    event: key_event, ..
} if key_event.state == ElementState::Pressed => match &key_event.logical_key {
    Key::Named(NamedKey::Escape) => return ConfirmationResult::Cancelled,
    Key::Character(ch) if ch == "n" || ch == "N" => {
        return ConfirmationResult::Cancelled;
    }
    Key::Character(ch) if ch == "y" || ch == "Y" => {
        return ConfirmationResult::Confirmed;
    }
    _ => {}
},

// ... widget dispatch (unchanged) ...

// After widget dispatch — check widget-flagged signals
if self.confirmed.load(Ordering::SeqCst) {
    ConfirmationResult::Confirmed
} else if self.cancelled.load(Ordering::SeqCst) {
    ConfirmationResult::Cancelled
} else {
    ConfirmationResult::None
}
Outcome: y key confirms at window level; Paste button click/focused-Enter confirms via widget dispatch + flag check. All T0003 cancellation routes (Escape, n, Cancel button) remain intact.

Step 5: Modify App window_event to send paste on Confirmed result

Files: src/app.rs

Action: Change the ConfirmationResult::Confirmed arm to extract raw_text from the confirmation window and send TerminalCommand::PasteText to the worker. The Cancelled arm remains unchanged (just dispose). Both arms already drop the window (the confirmation binding goes out of scope and is not reassigned to self.runtime.confirmation_window). 

match confirmation.handle_event(&event, scale) {
    confirmation::ConfirmationResult::Cancelled => {
        self.request_redraw(RedrawReason::Input);
        return;
    }
    confirmation::ConfirmationResult::Confirmed => {
        let raw_text = confirmation.raw_text().to_owned();
        if let Some(worker) = self.session.worker.as_ref() {
            let _ = worker.send(harbor_types::TerminalCommand::PasteText(raw_text));
        }
        self.request_redraw(RedrawReason::Input);
        return;
    }
    confirmation::ConfirmationResult::None => { /* unchanged */ }
}
Outcome: On confirm, unchanged raw content is forwarded through the existing PasteText terminal command. The terminal worker reads InputModes at send time and applies bracketed-paste framing. On cancel, no PTY bytes are written. The confirmation window and App gate are released in both cases.

4 Edge Cases

#ConditionExpected BehaviorOwning Step
1 User presses y while a non-Paste widget (e.g. Cancel) is focused y is a window-level shortcut checked before widget dispatch — it always confirms regardless of focus. The focused widget never sees the y key event. Step 4
2 User rapidly triggers both Cancel and Confirm (e.g., n followed by Paste button click in same frame, or both buttons clicked simultaneously) The first match in check order wins. Since window-level shortcuts are checked before widget dispatch, n would return Cancelled before checking confirmed flag. Within widget dispatch, both AtomicBools may be set, but the check order (confirmed first, then cancelled) decides. Either way, the window is disposed and the gate is released — no double-send or hang. Step 4
3 InputModes (especially bracketed_paste) change between dialog opening and user confirmation The terminal worker reads terminal.screen().input_modes() inside PasteText handler at the moment the paste bytes are written to the PTY. The modes at confirmation time are used, not the modes at dialog-open time. This is the expected behavior. Step 5
4 Confirmation window receives a KeyboardInput event that is neither a shortcut (y/n/Escape) nor routable to widget dispatch The event passes through both checks, no AtomicBool is set, and ConfirmationResult::None is returned. The window stays open. Step 4
5 Paste button receives Space key (which Button also handles) while focused Button's handle_event fires on_click for Space, setting the confirmed flag. Then post-dispatch flag check returns Confirmed. Consistent with Enter behavior. Step 3, Step 4

5 Test Strategy

ConfirmationWindow — raw_text storage and accessor

Verify raw_text() returns the exact string passed to new(), including newlines and special characters.
Mock None — pure data accessor, no dependencies.
Variations
  • Single-line text ("hello")
  • Multi-line text with \n and \r\n
  • Text containing Unicode and control characters

ConfirmationWindow — window-level keyboard shortcuts

Verify handle_event returns Confirmed for y/Y key press, Cancelled for n/N/Escape, and None for other keys. Shortcuts are checked before widget dispatch.
Mock None — synthetic winit WindowEvent::KeyboardInput events can be constructed directly in unit tests.
Variations
  • Lowercase "y" → Confirmed
  • Uppercase "Y" → Confirmed
  • Lowercase "n" → Cancelled
  • Escape → Cancelled
  • Other keys (e.g. "a", Enter without focused widget) → None
  • KeyRelease (not Pressed) → None

build_confirmation_root — widget tree structure and button callbacks

Verify The returned Component tree contains a TextLabel header, a Row with two Buttons. Paste button's on_click sets the confirmed flag. Cancel button's on_click sets the cancelled flag. Flags are independent.
Mock None — build with BuildCx::stub() and trigger on_click closures directly.
Variations
  • Paste button click sets confirmed only, not cancelled
  • Cancel button click sets cancelled only, not confirmed
  • Header text includes correct line count
  • Paste is first focusable widget (for default-focus priority)

ConfirmationWindow::handle_event — widget-flagged confirmation via AtomicBool

Verify After widget dispatch (simulated by pre-setting the AtomicBool), handle_event returns Confirmed when the confirmed flag is true, or Cancelled when the cancelled flag is true.
Mock Synthetic WindowEvent::RedrawRequested (which passes through to widget dispatch without matching shortcuts). Pre-set AtomicBool flags to simulate widget callback effects.
Variations
  • Confirmed flag set → Confirmed returned
  • Cancelled flag set → Cancelled returned
  • Both flags set → Confirmed returned (check order priority)
  • Neither flag set → None returned

App window_event — paste send on Confirmed

Verify On Confirmed, the App sends TerminalCommand::PasteText with the raw text to the worker and disposes the confirmation window. On Cancelled, the window is disposed without sending bytes. In both cases, the gate is released (confirmation_window is None).
Mock Integration-level: requires a ConfirmationWindow with known raw_text, a mock or real terminal worker channel, and synthetic events.
Variations
  • y key press → worker receives PasteText(raw_text), window disposed
  • Paste button click → worker receives PasteText(raw_text), window disposed
  • Cancel button click → worker receives no PasteText, window disposed
  • Escape key → worker receives no PasteText, window disposed
