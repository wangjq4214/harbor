Design Decisions

  • Separate TextRenderer, not extended QuadRenderer. Text glyphs use a textured pipeline with UV attributes and atlas sampling; quads use a solid-color pipeline. The two pipelines share no instance format or shader code. A separate type avoids conditional pipeline switching inside QuadRenderer and lets each be tested independently.
  • TextRunCache owned by Runtime, not a global. Each Runtime instance manages its own text content — the confirmation Runtime's text runs are unrelated to the main Runtime's. The cache's lifecycle matches the Runtime instance that owns it.
  • TextLabel as standalone widget, not merged into Button. Button is an interactive widget; TextLabel is a display-only widget. They have different intrinsic-size strategies (Button uses an estimate; TextLabel uses actual metrics), different paint outputs, and different event-handling behavior. Composing TextLabel into Button (or placing both in a Row) is cleaner than conditional rendering modes inside Button.
  • Button renders its own label via Primitive::Text. Button already owns the label string and uses it for sizing. Adding a Text primitive to its paint output is a natural extension — the button's visual label is an attribute of the button concept. This avoids requiring every Button user to manually embed a TextLabel child.
  • Confirmation root assembled in App, not a widget-crate type. The confirmation UI is a simple Column of a TextLabel header and a Cancel Button — no new widget abstraction is needed. The App already constructs widget trees; adding a paste-specific root component in harbor-widget would couple the widget crate to paste-domain concepts.
  • Escape and 'n' shortcuts handled at ConfirmationWindow, not in a widget. These are window-scoped shortcuts that always cancel, regardless of focus. A FocusScope-based approach would require the scope to intercept keys before the focused button, which conflicts with the capture→target→bubble ordering. The App-level handler (matching the existing PasteDialog pattern) is simpler and has clearer ownership.
  • Input gate is a boolean check in App, not a separate type. The gate is a single condition: if confirmation_window.is_some(), skip terminal keyboard forwarding and new paste creation. It has no independent state, lifecycle, or behavior beyond this check. Extracting it to a separate type would add indirection without a distinct concept boundary.

Step 1: Define TextRunCache and positioned-glyph types in harbor-widget

Files: crates/harbor-widget/src/text.rs

Action: Add PositionedGlyph struct (origin + AtlasUv + width + height) and TextRunCache struct with HashMap<TextRunId, Vec<PositionedGlyph>> storage. Expose register(text, metrics, glyph_fn) → TextRunId and get(id) → Option<&[PositionedGlyph]>. The register method iterates chars, looks up each glyph, computes monospace advance by cell_width, and stores the positioned result. Cache hit on identical (text, metrics) inputs returns the existing id.

// PositionedGlyph: per-glyph draw data
struct PositionedGlyph {
    origin: Point,      // top-left in dp
    width: f32,
    height: f32,
    uv_left: f32,
    uv_top: f32,
    uv_right: f32,
    uv_bottom: f32,
    color: [f32; 4],
}

// TextRunCache: TextRunId → glyphs
struct TextRunCache {
    runs: HashMap<TextRunId, Vec<PositionedGlyph>>,
    next_id: TextRunId,
    // (text, metrics_hash) → id for dedup
    dedup: HashMap<(String, u64), TextRunId>,
}

impl TextRunCache {
    fn register(
        &mut self,
        text: &str,
        metrics: &TextMetrics,
        glyph_fn: &impl Fn(char) -> Option<AtlasGlyph>,
        color: Color,
    ) -> TextRunId;

    fn get(&self, id: TextRunId) -> Option<&[PositionedGlyph]>;
}

Step 3: Modify Button to render its label as text

fn paint_primitives(&self, rect: Rect) -> Vec<Primitive> {
    let bg = state.background_color();
    let border = state.border_color();
    let label_color = Color::WHITE; // or computed from state
    let label_origin = Point::new(
        rect.min.x + horizontal_padding / 2.0,
        rect.min.y + (rect.size().height - line_height) / 2.0,
    );
    vec![
        Primitive::Quad { rect, color: bg, corner_radius },
        Primitive::Border { rect, width: 1.0, color: border, corner_radius },
        Primitive::Text { run: self.label_run_id(), origin: label_origin, color: label_color },
    ]
}

Step 10: Implement App-level cross-window input gate (ADR 0009)

4 Edge Cases

#ConditionExpected BehaviorOwning Step
1 Confirmation window is open and user triggers another confirmable paste The App gate blocks creation of a second confirmation window. The second paste is silently dropped (no-op). The existing confirmation window remains. Step 10
2 Glyph lookup returns None for a character (missing glyph in atlas) TextRunCache::register skips the character — advances the pen by cell_width without emitting a glyph quad. The text label renders a gap for the missing character rather than panicking. Step 1
3 Empty text string for TextLabel or Button label TextRunCache::register returns a run with zero glyphs. TextRenderer::encode_run is a no-op. The widget's intrinsic width is zero (clamped to constraints minimum). Step 1, 4
4 Confirmation window is closed by the OS (e.g., Alt+F4, taskbar close) WindowEvent::CloseRequested is treated as cancellation — same result as clicking Cancel. No PTY bytes sent. Step 8
5 Main window surface is lost or occluded while confirmation window is open Main window rendering path handles surface loss independently (existing render_frame retry logic). Confirmation window is unaffected — it has its own surface. Gate remains active. Step 10
6 Confirmation window surface is lost or suboptimal during render ConfirmationWindow::render handles SurfaceTexture::Lost/Outdated/Suboptimal with reconfiguration, matching the main window pattern. A lost surface during cancel does not prevent resource cleanup. Step 8
7 DPI changes on either window while the confirmation window is open The confirmation Runtime's viewport receives the updated scale factor via set_viewport. Text layout and hit testing use the new scale factor. The main window continues its own independent DPI handling. Step 11
8 Text run cache accumulates stale runs across multiple confirmation window instances Each ConfirmationWindow owns its own Runtime, which owns its own TextRunCache. When the confirmation window is dropped, the cache is dropped with it. No cross-instance leakage. Step 5, 8
