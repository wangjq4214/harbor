#1: Clear Responsibility — ConfirmationWindow mixes GPU, winit, widget runtime, and paste data Priority 4/5

📍 src/app/confirmation.rs:107-119 (ConfirmationWindow struct + impl)

Problem

The ConfirmationWindow struct has 12 fields spanning four distinct concerns: GPU resources (surface, surface_config), a winit Window, a widget Runtime, paste business data (raw_text, wrapped_lines), and shared atomic state flags (cancelled, confirmed). Its methods — handle_event, render, scale_factor_changed, resize — all interleave surface configuration, viewport math, widget runtime dispatch, and flag checking. Testing any single concern (e.g., keyboard shortcuts) currently requires constructing a full winit window with a GPU surface.

pub(crate) struct ConfirmationWindow {

    surface_config: wgpu::SurfaceConfiguration, // GPU config
    runtime: Runtime,                       // widget framework
    raw_text: String,                       // paste data
    cancelled: Arc<AtomicBool>,             // shared state flag
    confirmed: Arc<AtomicBool>,             // shared state flag
    wrapped_lines: Vec<String>,             // paste data display
    preview_scroll_offset: Arc<AtomicUsize>, // shared state
    preview_line_height: f32,               // layout cache
    preview_max_chars: usize,               // layout cache
}

Fix Strategy

1. Extract a GpuWindow struct that owns Window + Surface + SurfaceConfiguration and exposes render_frame, resize, scale_factor_changed.

2. Extract a DialogController that owns the Runtime, paste data, and flags, and exposes handle_event → ConfirmationResult.

3. ConfirmationWindow composes GpuWindow + DialogController, delegating instead of inlining GPU configuration.

4. Unit-test DialogController with a mock widget runtime — no winit window or GPU needed.

Expected Benefit

Keyboard shortcut logic (y/n/Escape) and confirmation flow become independently testable without creating a GPU window. The GpuWindow is reusable for any future secondary window (settings, error banners). Surface recovery logic lives in one place.

#2: Clear Responsibility — Selection mixes domain model, GPU pipeline, clipboard, and event controller Priority 4/5

📍 crates/harbor-render/src/selection.rs:19-38 (Selection struct)

Problem

The Selection struct in harbor-render combines four distinct roles: a domain model (SelectionModel), GPU resources (pipeline, vertex_buffer), I/O (clipboard), and event-handling controller logic (handle_event at 200 lines). The handle_event method alone dispatches keyboard shortcuts (Ctrl+C/V, Shift+Insert), mouse press/drag/release, cursor tracking, auto-scroll, and focus loss — all with inline business logic mixed with GPU state manipulation. A new selection behavior requires reading ~400 lines of intertwined model/GPU/event code.

pub struct Selection {
    model: SelectionModel,           // domain: selection range + state machine
    pipeline: Arc<RenderPipeline>,   // GPU: shader pipeline
    vertex_buffer: wgpu::Buffer,     // GPU: vertex data
    vertex_count: u32,               // GPU: draw count
    last_cursor_pos: Option<(f64,f64)>, // controller: cached input
    pending_copy: Option<u64>,       // controller: async state
    cell_width: f32, line_height: f32, // layout cache
    dirty: bool,                     // GPU: upload flag
    clipboard: Option<Clipboard>,    // I/O resource
}

Fix Strategy

1. Keep SelectionModel as a pure domain type (generation-based range, press/drag/release/clear state machine). It already exists.

2. Extract a SelectionGpu struct owning the pipeline, vertex buffer, and prepare / draw methods — a pure GPU resource type.

3. Create a SelectionController in harbor-render that owns SelectionModel + SelectionGpu + Clipboard, and exposes handle_event / on_about_to_wait. This separates the controller concern from the resources it coordinates.

4. The Component trait impl becomes a thin delegation on SelectionController: prepare calls self.gpu.prepare, draw calls self.gpu.draw.

Expected Benefit

Selection business logic (Ctrl+C copy, double-click word selection, drag auto-scroll) is testable without a GPU context. The GPU upload path is isolated in SelectionGpu. Adding a new selection behavior (e.g., rectangular block select) touches only the controller, not the GPU code.

#3: Leaked State — Widget callbacks mutate shared atomic flags read by ConfirmationWindow Priority 3/5

📍 src/app/confirmation.rs:113-116 (Arc flags), :317-322 (flag checking)

Problem

The Cancel and Paste buttons in the confirmation dialog are wired via Arc<AtomicBool> flags (cancelled, confirmed) that the widget callbacks set. ConfirmationWindow::handle_event reads these flags after each event dispatch:

// Widget callbacks capture Arcs:
let cancelled = Arc::new(AtomicBool::new(false));
let confirmed = Arc::new(AtomicBool::new(false));
// ... passed into Button callbacks that set them to true ...

// ConfirmationWindow reads them back:
if self.confirmed.load(Ordering::SeqCst) {
    ConfirmationResult::Confirmed
} else if self.cancelled.load(Ordering::SeqCst) {
    ConfirmationResult::Cancelled
}

This creates a side channel — widget state "leaks" out through atomics rather than through the widget runtime's event system. The SeqCst ordering is the strongest barrier, hinting that the developer wasn't confident in the visibility guarantees. Testing the full flow requires both the widget tree AND the atomic flag polling.

Before

graph LR B[Button Callback] -->|AtomicBool::store| F[confirmed/cancelled] CW[ConfirmationWindow] -->|AtomicBool::load| F

After

graph LR B[Button Callback] -->|UiEvent| R[Widget Runtime] R -->|ExternalEvent| CW[ConfirmationWindow] CW -->|ConfirmationResult| C[Caller]

Fix Strategy

1. Instead of Arc<AtomicBool>, have the button callbacks send a custom UiEvent variant (e.g., UiEvent::Action(Action::ConfirmPaste)).

2. ConfirmationWindow::handle_event reads the action from the runtime's drain_external_input() queue — the same channel already used for keyboard events from focused widgets.

3. Remove the cancelled and confirmed fields from ConfirmationWindow entirely. The ConfirmationResult::Cancelled path is already handled by Escape key check — the Cancel button just needs to post the same action.

Expected Benefit

All widget-to-host communication flows through a single typed channel. No Arc<AtomicBool> shared between UI callbacks and host code. The confirmation flow is trivially testable by injecting UiEvent::Action into the runtime.

#4: Clear Responsibility — confirmation.rs packs window mgmt, widget tree, and tests in one 965-line file Priority 3/5

📍 src/app/confirmation.rs:1-965 (entire file)

Problem

confirmation.rs at 965 lines contains three separate concerns: winit window + wgpu surface management (~300 lines), widget tree construction via build_confirmation_root (~200 lines), and ~430 lines of tests. The widget tree construction (build_confirmation_root) builds a FocusScope → Padding → Column → [TextLabel, PreviewPane, Row → [Button, SizedBox, Button]] hierarchy that is conceptually "what the dialog looks like", separate from "how the dialog window works". A developer wanting to change the dialog layout must read GPU surface configuration code to find the widget tree.

// Same file mixes:

// ── Tests (lines 535-965, over 430 lines!)

After

4. If extracting GpuWindow, ConfirmationWindow becomes ~200 lines of dialog-specific logic, and the widget tree builder gets its own module.

Expected Benefit

Changing the dialog layout (adding a "Don't ask again" checkbox) requires editing only the widget tree file, not the surface management code. The GPU window abstraction is reusable for error banners, settings, or any future secondary window.

#5: Method Placement — Paste/confirmation text utilities live in harbor-types, far from their sole consumer Priority 2/5

📍 crates/harbor-types/src/lib.rs (safe_preview_line, should_confirm_multiline) → src/app/confirmation.rs

Problem

Two paste-related text utilities live in harbor-types — the foundational "no dependency" crate — but are consumed only by confirmation.rs and re-exported through harbor-terminal:

// harbor-types/src/lib.rs — foundational crate, no dependencies
pub fn safe_preview_line(line: &str) -> String { ... }  // only used in confirmation.rs
pub fn should_confirm_multiline(text: &str) -> bool { ... }  // only used in confirmation.rs

// harbor-terminal/src/lib.rs re-exports:
pub use harbor_types::should_confirm_multiline;
pub use harbor_types::{ ..., safe_preview_line, ... };

These are presentation-level utilities (escaping control characters for preview display, deciding whether to show a confirmation dialog) that have nothing to do with the shared type definitions in harbor-types. Their presence there means harbor-types is slowly accumulating utility functions that belong at the application level.

Before

graph TD HT[harbor-types] --> SP[safe_preview_line] HT --> SC[should_confirm_multiline] CR[confirmation.rs] --> HT CR -->|sole consumer| SP CR -->|sole consumer| SC

After

graph TD CR[confirmation.rs] --> SP2[safe_preview_line] CR --> SC2[should_confirm_multiline] HT[harbor-types] --> T[Types only]

Fix Strategy

1. Move safe_preview_line into src/app/confirmation.rs (its sole consumer).

2. Move should_confirm_multiline into src/app/confirmation.rs or crates/harbor-render/src/selection.rs where PasteDisposition::decide already lives.

3. Remove the re-exports from harbor-terminal/src/lib.rs and delete the original functions from harbor-types/src/lib.rs.

4. harbor-types returns to being purely type definitions with zero utility functions — as intended by its position at the bottom of the dependency graph.

Expected Benefit

harbor-types stays a pure type-definition crate with no business logic. Changing confirmation-dialog behavior no longer pulls in a foundational crate. The dependency direction is correct: application code depends on types; types don't carry application-specific utilities.
